# 1. Process Governance: Definition of Ready (DoR) and Done (DoD)

**Definition of Ready (DoR):** A story is Ready when it follows standard user story syntax, links directly to official FR IDs (FR-01..FR-21), has testable Given/When/Then acceptance criteria covering exact HTTP error codes, maps to OpenAPI operationIds or marks them planned, carries a Fibonacci estimate (\<= 8 pts), states acyclic prerequisites, designates a role owner, and is approved by the PO.

**Definition of Done (DoD):** A story is Done when the work satisfies all acceptance criteria, is developed on a feature branch, is merged into develop through a pull request with at least one approving review, and conforms to the OpenAPI contract.

# 3. Epic 1: User Management

**US-01: User Registration & Authentication (#1)** • User Story: As a prospective adopter or shelter owner, I want to register an account and securely log in, so that I can use the functions permitted for my role (browsing and applying as an Adopter, managing listings and applications as a Shelter Owner). Admin accounts are not created through public registration (A-03). • Official FR ID: FR-01, FR-02 \| Priority: High \| Points: 3 \| Owner: IMPL \| Deps: None \| Placeholder: \#1 • OpenAPI operationId: registerUser, loginUser, logoutUser **• Acceptance Criteria:** - Scenario 1 (Registration): GIVEN valid adopter details, WHEN POST /auth/register, THEN system returns 201 Created with User entity containing banned: false (excluding JWT token). - Scenario 2 (Duplicate Email): GIVEN existing user email, WHEN POST /auth/register with same email, THEN returns 409 Conflict. - Scenario 3 (Login): GIVEN registered user with banned: false, WHEN POST /auth/login with valid password, THEN returns 200 OK with LoginResponse containing JWT bearer token. - Scenario 4 (Bad Password): GIVEN registered user, WHEN POST /auth/login with wrong password, THEN returns 401 Unauthorized. - Scenario 5 (Shelter Owner Account): GIVEN valid details with role SHELTER_OWNER, WHEN POST /auth/register, THEN 201 Created with role SHELTER_OWNER; publishing listings still requires an approved shelter registration (US-02, US-03, A-04). - Scenario 6 (Logout): GIVEN a logged-in user, WHEN POST /auth/logout, THEN 204 No Content.

**US-02: Shelter Owner Registration Request (#2)** • User Story: As a shelter representative, I want to submit a shelter registration request with organization credentials, so that an administrator can verify our credentials before we post animal listings. • Official FR ID: FR-03 \| Priority: High \| Points: 3 \| Owner: IMPL \| Deps: \#1 \| Placeholder: \#2 • OpenAPI operationId: Planned / not yet specified in draft OpenAPI **• Acceptance Criteria:** - Scenario 1 (Submission): GIVEN valid shelter credentials, WHEN registration submitted, THEN 201 Created with a pending status queued for Admin review. - Scenario 2 (Locked Capabilities): GIVEN a shelter whose registration is not yet approved, WHEN POST /animals attempted, THEN 403 Forbidden (A-04). **Note:** The exact shelter registration status names are pending OI-04.

# 4. Epic 2: Admin Management

**US-03: Review and Decision on Shelter Registrations (#3)** • User Story: As a System Administrator, I want to review pending shelter registration applications and approve or reject them, so that only legitimate animal shelters operate on the platform. • Official FR ID: FR-03, FR-04 \| Priority: High \| Points: 5 \| Owner: ARCH \| Deps: \#2 \| Placeholder: \#3 • OpenAPI operationId: Planned / not yet specified in draft OpenAPI **• Acceptance Criteria:** - Scenario 1 (Approve): GIVEN Admin and pending shelter, WHEN approved, THEN status Approved, audit logged, 200 OK. - Scenario 2 (Reject): GIVEN Admin and pending shelter, WHEN rejected, THEN status Rejected, status change persisted, 200 OK. - Scenario 3 (Forbidden): GIVEN non-admin user, WHEN accessing approval endpoints, THEN 403 Forbidden. **Note:** The exact shelter registration status names (shown here as Approved / Rejected) are pending OI-04.

**US-04: User Ban and Unban Management (#4)** • User Story: As a System Administrator, I want to ban or unban users who violate platform rules or animal welfare standards, so that suspended individuals cannot participate in adoption workflows. • Official FR ID: FR-06 \| Priority: Medium \| Points: 3 \| Owner: QA \| Deps: \#1, \#3 \| Placeholder: \#4 • OpenAPI operationId: Planned / not yet specified in draft OpenAPI **• Acceptance Criteria:** - Scenario 1 (Ban): GIVEN Admin inspecting user, WHEN banned, THEN banned is set to true, audit logged, 200 OK. - Scenario 2 (BR-07 Automatic Rejection): GIVEN adopter has Pending adoption applications, WHEN Admin bans adopter, THEN all Pending applications automatically become Rejected, while previously Approved applications remain unchanged. The ban operation and the automatic rejection of all Pending applications must be completed atomically within the same database transaction, and every rejection is recorded in the status history (BR-09). - Scenario 3 (Unban): GIVEN banned user, WHEN unbanned, THEN banned is set to false, 200 OK.

**US-05: Animal Listing Moderation (#5)** • User Story: As a System Administrator, I want to moderate inappropriate or non-compliant animal listings using the actions authorized by FR-05, so that public listings conform to platform policies.  
• Official FR ID: FR-05 \| Priority: Medium \| Points: 3 \| Owner: QA \| Deps: \#3, \#7 \| Placeholder: \#5 • OpenAPI operationId: archiveAnimal (Admin is allowed by FR-05); a separate remove operation is not defined (OI-06) • Acceptance Criteria: GIVEN an Available listing and an Admin-authorized archive action, WHEN the Admin archives the listing, THEN its status becomes Archived, it is excluded from available-animal search, and the change is audit logged. The meaning and behavior of the separate “remove” action remain unresolved under OI-06; no removal behavior or API endpoint is assumed here.

# 5. Epic 3: Shelter Management

**US-06: Shelter Profile Management (#6)** • User Story: As an approved Shelter Owner, I want to maintain our shelter's public profile, address, operating hours, and contact information, so that prospective adopters have accurate shelter information. • Official FR ID: FR-07 \| Priority: Medium \| Points: 2 \| Owner: IMPL \| Deps: \#3 \| Placeholder: \#6 • OpenAPI operationId: Planned / not yet specified in draft OpenAPI • Acceptance Criteria: GIVEN authenticated Shelter Owner, WHEN updating address/hours/phone with valid data, THEN saved to DB and returns 200 OK.

**US-07: Create and Publish Animal Listing via Image URL (#7)** • User Story: As an approved Shelter Owner, I want to create a new animal listing with characteristics and public Image URLs, so that adopters can discover and apply for the animal. • Official FR ID: FR-08 \| Priority: High \| Points: 5 \| Owner: IMPL \| Deps: \#6 \| Placeholder: \#7 • OpenAPI operationId: createAnimal **• Acceptance Criteria:** - Scenario 1 (Valid Listing): GIVEN approved Shelter Owner with valid data (name, species, age) and HTTP/HTTPS image URL, WHEN POST /animals, THEN status Available, audit logged, 201 Created. - Scenario 2 (Invalid URL): GIVEN non-HTTP/HTTPS image string, WHEN POST /animals, THEN returns 400 Bad Request.

**US-08: Update & Archive Animal Listing (#8)** • User Story: As a Shelter Owner, I want to update animal listing details using PATCH or archive a listing instead of permanently deleting it, so that adoption histories and auditability are preserved. • Official FR ID: FR-09 \| Priority: High \| Points: 3 \| Owner: ARCH \| Deps: \#7 \| Placeholder: \#8 • OpenAPI operationId: updateAnimal, archiveAnimal **• Acceptance Criteria:** - Scenario 1 (Update via PATCH): GIVEN animal in Available status, WHEN PATCH /animals/{id} with fields, THEN record updates and 200 OK; the status does not change, so no status history entry is created. - Scenario 2 (Archive / Soft Delete): GIVEN animal listing in Available status, WHEN POST /animals/{id}/archive, THEN status transitions from Available to Archived, permanent deletion blocked, 200 OK. - Scenario 3 (Forbidden): GIVEN Shelter A, WHEN modifying animal of Shelter B, THEN 403 Forbidden. - Scenario 4 (Archive Conflict): GIVEN animal in Reserved, Adopted or Archived status, WHEN POST /animals/{id}/archive, THEN 409 Conflict.

**US-09: Physical Handover Confirmation (#9)** • User Story: As a Shelter Owner, I want to record the physical handover of a reserved animal to the approved adopter, so that the animal status is officially finalized as Adopted. • Official FR ID: FR-12 \| Priority: High \| Points: 5 \| Owner: ARCH \| Deps: \#14 \| Placeholder: \#9 • OpenAPI operationId: recordHandover **• Acceptance Criteria:** - Scenario 1 (Handover Success): GIVEN animal in Reserved status with approved app, WHEN POST /animals/{id}/handover, THEN status transitions to Adopted, ownerAdopterId is set to the approved adopter, the status change is recorded, 200 OK. - Scenario 2 (Conflict on Non-Reserved): GIVEN animal in Available or Archived status, WHEN POST /animals/{id}/handover executed, THEN returns 409 Conflict.

# 7. Epic 5: Adoption Management

**US-12: Submit Adoption Application with Mandatory Document Links (#12)** • User Story: As an authenticated Adopter, I want to submit an adoption application for an available animal, attaching mandatory document links and apartment permission if I live in an apartment and am applying for a dog, so that the shelter can evaluate my application. • Official FR ID: FR-16 \| Priority: High \| Points: 5 \| Owner: ARCH \| Deps: \#1, \#7, \#11 \| Placeholder: \#12 • OpenAPI operationId: submitApplication **• Acceptance Criteria:** - Scenario 1 (Intake Success): GIVEN authenticated adopter with banned: false, WHEN POST /applications for Available animal with valid docs, THEN status Pending, audit logged, 201 Created. - Scenario 2 (Apartment Dog Rule): GIVEN adopter living in apartment applying for Dog without documents: \[{ type: APARTMENT_PERMISSION, url }\], WHEN submitted, THEN returns 422 Unprocessable Content. - Scenario 3 (Banned User Block): GIVEN user with banned: true, WHEN submitting, THEN returns 403 Forbidden. - Scenario 4 (Multi-Applicant Intake): GIVEN animal with existing Pending app from User A, WHEN User B applies for same animal, THEN User B app created as Pending (201 Created). - Scenario 5 (Animal Not Available): GIVEN animal in Reserved, Adopted or Archived status, WHEN POST /applications, THEN 409 Conflict. - Scenario 6 (Unknown Animal): GIVEN animalId that does not exist, WHEN POST /applications, THEN 404 Not Found.

**US-13: Adopter Application Tracking and Withdrawal (#13)** • User Story: As an Adopter, I want to track the status of my submitted applications and withdraw any application that is still pending, so that I can cancel my request if my circumstances change. • Official FR ID: FR-17, FR-18 \| Priority: Medium \| Points: 3 \| Owner: IMPL \| Deps: \#12 \| Placeholder: \#13 • OpenAPI operationId: listApplications, withdrawApplication **• Acceptance Criteria:** - Scenario 1 (Tracking): GIVEN authenticated adopter, WHEN GET /applications, THEN 200 OK with list of user applications and real-time statuses. - Scenario 2 (Withdraw Pending): GIVEN application in Pending status, WHEN POST /applications/{id}/withdraw, THEN status Withdrawn, audit logged, 200 OK. - Scenario 3 (Conflict on Non-Pending): GIVEN application in Approved, Rejected or Withdrawn status, WHEN POST /applications/{id}/withdraw executed, THEN returns 409 Conflict. - Scenario 4 (Other Adopter's Application): GIVEN application of another adopter, WHEN POST /applications/{id}/withdraw, THEN 403 Forbidden.

**US-14: Review, BR-08 Quota Check & Atomic Approval (#14)** • User Story: As a Shelter Owner, I want to review submitted applications and approve one candidate while enforcing the BR-08 quota and automatically rejecting all other pending applicants for that animal, so that the animal is safely reserved without double-booking. • Official FR ID: FR-10, FR-11, FR-19, FR-20 \| Priority: High \| Points: 8 \| Owner: ARCH \| Deps: \#12 (Acyclic; no dependency on \#9) \| Placeholder: \#14 • OpenAPI operationId: listApplications, approveApplication, rejectApplication **• Acceptance Criteria:** - Scenario 1 (Atomic Single Approval & Auto-Rejections): GIVEN Animal A (Available) with Apps 1, 2, 3 (Pending) and the applicant has fewer than three animals in Reserved or Adopted status, WHEN POST /applications/1/approve, THEN in an atomic transaction: (1) App 1 becomes Approved, (2) Animal A becomes Reserved, (3) Apps 2 & 3 become automatically Rejected, (4) Audit logs saved, (5) returns 200 OK. - Scenario 2 (BR-08 Quota Rejection at Approval): GIVEN adopter already has three animals in Reserved or Adopted status, WHEN another application approval is attempted, THEN system prevents approval and returns 422 Unprocessable Content. - Scenario 3 (Concurrency on Same Animal): GIVEN two concurrent approvals for same animal arrive simultaneously, WHEN transaction lock resolves, THEN exactly one succeeds (200 OK) and other fails with 409 Conflict. - Scenario 4 (Concurrency on Quota): GIVEN adopter has two pending applications on different animals and already has two Reserved/Adopted animals, WHEN both approvals arrive concurrently, THEN exactly one succeeds (total 3) and the other fails with 422 Unprocessable Content. - Scenario 5 (Single Approval Enforced): GIVEN animal already in Reserved or Adopted, WHEN another approval attempted, THEN returns 409 Conflict. - Scenario 6 (Manual Reject): GIVEN Pending application, WHEN POST /applications/{id}/reject, THEN status Rejected, animal remains Available, 200 OK. - Scenario 7 (Review Applications, FR-10): GIVEN a Shelter Owner, WHEN GET /applications?animalId={id}, THEN 200 OK returns only applications for animals of their own shelter; requesting another shelter's application by ID returns 403 Forbidden. - Scenario 8 (Missing Documents, BR-05/BR-06): GIVEN a Pending application with a missing mandatory document (for example, no APARTMENT_PERMISSION for a dog when the adopter lives in an apartment), WHEN approval is attempted, THEN 422 Unprocessable Content and no status changes.

**US-15: Status History and Immutable Audit Logging (#15)** • User Story: As an Administrator or Shelter Owner, I want all state changes to animals and applications to be recorded with responsible user ID and timestamp, so that all operational actions are auditable and accountable. • Official FR ID: FR-21 \| Priority: High \| Points: 3 \| Owner: DEVOPS \| Deps: \#1, \#8, \#14 \| Placeholder: \#15 • OpenAPI operationId: getAnimalStatusHistory, getApplication (General system audit query planned) **• Acceptance Criteria:** - Scenario 1 (Auto Logging): GIVEN state change on Animal or Application, WHEN transaction commits, THEN immutable record inserted into status history with entity_type, entity_id, previous_status, new_status, actor_user_id, timestamp. - Scenario 2 (Immutability): GIVEN existing status history records, WHEN API client attempts modification or deletion, THEN no API operation can modify or delete status history records. - Scenario 3 (Inspection): GIVEN an animal or application with recorded transitions, WHEN GET /animals/{animalId}/status-history or GET /applications/{applicationId} is requested, THEN 200 OK returns chronological status history (for an application, through ApplicationDetail.statusHistory).

# 8. Open Issues and Clarification Topics

**• OI-01:** Undefined exit from Reserved status if an approved adopter abandons the adoption prior to physical handover (Open). **• OI-02:** Count of Reserved animals in adoption quota (Closed: Reserved animals count toward the limit per BR-08). **• OI-03:** Status of pending applications for post-banned users (Closed: Pending applications automatically rejected per BR-07). **• OI-04:** Shelter registration statuses (Open). **• OI-05:** Supported species enumeration (Open). **• OI-06:** Interpretation of 'Remove' in FR-05 (Open). **• OI-07:** Mandatory documents list beyond apartment permission (Open). **Additional Open Issues (Pending Discussion):** Document MIME type validation, Reservation timeout window, Multi-shelter staff relationships.
